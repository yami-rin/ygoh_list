# 実コア探索の性能計測

2026-09-08 07:06 JST、Windows / Node v24.19.0 で計測した。共有の `engine.mjs`、探索カーネル、実対戦プロセスは変更していない。Astra CLI の呼び出し、追加ワーカープロセスの起動も行っていない。

現条件では、WASMコンパイル結果の共有と探索内部での画面用snapshot生成省略により、処理量が **41.33 → 55.45 fixture/秒、約34%増**となった。実行時のライブラリまで32回再利用する実験は58.32 fixture/秒だったが、ラッパーのコールバック保持が実証されており、長期間の使い回しを正当化する結果ではない。共有実装への採用判断は主担当へ渡した。

統合では、コンパイル済みModuleだけの共有と探索内部のsnapshot省略を採用した。各duelのInstance・メモリ・Lua・コールバックは新規生成する。通常の対戦APIは従来どおりsnapshotを返す。統合後に実core・通信契約・探索・多重起動防止を含む41テストと、展開帳の51ルート＋63 probeの独立再生が通過した。この計測は探索処理の速度であり、対戦中のAstraの思考時間短縮を測ったものではない。

## 再現

`duel-lab` で実行する。

```powershell
node --expose-gc scripts/benchmark-core-search.mjs --iterations=200
```

今回の終了コードは0。標準エラーに各方式の要約、標準出力に全測定値と同一性・HOPT検証結果のJSONを出す。`--iterations=4` は計測スクリプトの動作確認用で、速度比較の根拠には使わない。

- WASM SHA-256: `68e0ddde6932df1dc9de39e6eff8afae10a5db0f18ea8a0870a6b7eb80073ea8`
- preset SHA-256: `8d4d40bc085644f9150344c6237b4239a07ef69f1cc21631832b4b695b641095`
- ルート: Rabbit→I:P 58応答、Dormouse→Crypter 73応答、Cat→Decoder 5応答。
- 深さ0、8、32、終端までのprefixを各方式200回、7方式で計1,400回実行した。短いルートは長さで打ち切る。同じfixtureの反復を含み、1,400通りの異なる展開を探索したという意味ではない。
- 通常の `Duel.create` と既存ルートの各入力前ハッシュ・終端ハッシュを先に照合し、それを独立した比較基準とした。全方式のprefix終了時の盤面・保留中の選択肢ハッシュが一致した。

## 時間内訳

すべて1fixtureあたりの平均。`初期化` はライブラリ生成、duel生成、基礎Lua読込、カード追加、最初の選択待ちまでの処理を含む。`prefix再生` は通常APIのsnapshot生成と終端の証拠ハッシュ作成を含む。snapshot省略方式も応答の `responseFor` 検証と実コアによる効果処理は維持している。

| 方式 | 初期化 ms | prefix再生 ms | fixture/秒 |
|---|---:|---:|---:|
| 毎回WASMファイル読込・新規ライブラリ | 19.09 | 4.39 | 41.33 |
| WASMバイト列のみキャッシュ | 16.94 | 3.78 | 46.81 |
| コンパイル結果を共有・新規ライブラリ | 15.53 | 3.65 | 50.44 |
| ライブラリを最大32duelで交換 | 13.93 | 3.34 | 56.19 |
| ライブラリを200duelで交換する実験 | 13.68 | 3.07 | 57.90 |
| コンパイル結果共有＋snapshot省略 | 15.69 | 1.72 | 55.45 |
| 最大32duelで交換＋snapshot省略 | 14.95 | 1.64 | 58.32 |

コンパイル結果共有・新規ライブラリの内訳は、ライブラリ生成0.52ms、duel handle生成0.32ms、基礎Lua読込・実行10.58ms、カード追加3.92ms、開始処理0.19ms。初期化を支配するのはLuaの読込・実行である。WASMコンパイル自体は開始時に1.86msだった。

カードreaderは平均41回、script readerは平均66回。JS側のreaderコールバックに費やした合計は平均0.18msで、Luaコードの解析・実行時間を含まない。カードDB JSONの初回importもこの表の反復計測には含めていない。

長いprefixでは画面用snapshotの費用も大きい。コンパイル結果共有方式のDormouse 73応答は、通常APIで13.44ms、snapshot生成を省くと5.77msだった。32応答は6.25ms→2.64ms。探索内部が現在の選択待ちを所有している場合に限り、このデータ生成を省く余地がある。対戦UIの応答、プレイヤー・revision検証まで省略する提案ではない。

計測は単一プロセスで方式を順番に実行した。JIT、GC、同じPCの別作業、短期のCPU変動を完全には除去していないため、この倍率を本番の並列探索速度へそのまま転記しない。

## 再利用の分離検証

すべての実験で、JSの `Duel` オブジェクトとネイティブduel handleは毎回新規作成し、終了時に `destroyDuel` を呼んだ。既存盤面のhandleを巻き戻して使い回す方式は試していない。

追加で、同一ライブラリ内に独立したduelを200回生成し、実カードのDormouseを表側で2体置いたfixtureを試した。これは同名HOPTの確認専用であり、固定デッキの実戦用レシピではない。

1. 毎回の初期状態で、双方のDormouseにデッキ除外効果の発動候補が存在する。
2. 交互に片方を選び、Rabbitを除外する。任意の帰還は断る。
3. デッキには有効な除外対象のCatが1体残るが、双方のDormouseから発動候補が消える。
4. 600ATK上昇が双方に適用される。
5. duelを破棄して次を生成すると、双方の発動候補が復帰する。

200回ともPASS。固定した3ルートの各prefixも全方式で一致した。この結果は、確認したカードとLuaの範囲で状態の分離を裏付けるもので、全スクリプト・全裁定・同時に生存する複数duelの安全性を証明しない。

## ラッパーの保持問題

現在インストールされている `ocgcore-wasm` 0.1.2 の `dist/index.js` と、そのsource map内 `src/index.ts` を確認した。source mapの101行付近でcallbackのMapを作り、140〜147行付近の `createDuel` がreader/error handlerを追加する。410〜412行付近の `destroyDuel` はネイティブ破棄だけを実行し、Mapから削除しない。プロジェクトの `errorHandler` はそのduelオブジェクトを参照している。

計測スクリプトでは、error handlerだけから参照される小さなpayloadを用意し、ネイティブduelを破棄した後にイベントループを進め、明示GCを2回実行した。ライブラリを保持したままだと `WeakRef.deref()` はpayloadを返した。**ネイティブ破棄だけではJS側のコールバックが解放されない**ことを実測した。

さらにreader経路はsetcodesを `_malloc` し、duel作成時の `cardReaderDone` は0である。ただし、これだけからネイティブ側の解放漏れの規模までは断定していない。RSSもGCとアロケータの影響を受ける。32duel交換方式の1回の計測ではRSSが約138MB→249MBに増えたため、上限を付ければ一定メモリ量になると主張する証拠にも使えない。

コンパイル済み `WebAssembly.Module` だけを共有し、新しい `WebAssembly.Instance` とライブラリを生成する方式は、この保持期間をライブラリの寿命へ限定する。使った `instantiateWasm(imports, receive)` はラッパーの型定義には記載されていないが、現固定バージョンがオプションをEmscriptenへ渡す実装と実行結果の両方で確認した。依存更新時は再検証が必要になる。

基礎Luaの読み飛ばし、既存Lua VMの状態初期化、WASM heapの複製、長時間の無制限poolは実装・検証していない。共有実装に組み込む場合も、この計測とは別に実際の探索カーネルの継続・中断・エラー経路を検証する必要がある。
