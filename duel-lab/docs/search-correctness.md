# 1枚初動探索の独立検証

2026-09-08。対象は固定された通常M∀LICEプリセット、先攻、相手の初期手札・盤面なし、開始手札は指定した1枚のみ。実戦の残り4枚による分岐、相手の妨害、未知のドロー全結果を、この条件の探索済み件数に含めない。

## 実行証拠

`tests/search-enumeration-audit.test.mjs`は22件。最初の11件が応答・取引、次の6件がv2探索器、続く3件がドロー継続、最後の2件が逆順証拠の読み戻しと同名カードの添字分岐。各対象を変更に応じて実行し成功した。逆順証拠の読み戻しは、未追跡runtime監査ファイルがない環境ではスキップする。今回の実行ではスキップなし。

## 監査中に検出した互換性不具合

1. `SELECT_SUM`の必須・任意グループが逆に読まれ、各カードの位置フィールド4バイトが読み飛ばされていた。サブテラーの戦士の実際の要求で、2枚目のカードIDが3、コントローラーが254となる破損を再現した。
2. `SORT_CARD`の応答先頭に余分な並べ替え枚数が入り、正しい逆順を送っても実エンジンがRETRYを返していた。
3. 必須素材を含むSUMで、応答側が必須分の添字を再度追加していた。互換担当が実エンジンで不正応答を再現し、任意素材の添字だけを送るよう修正した。監査側の変換テストもこの通信契約へ追従した。

互換パッチ担当の`patch-core.mjs`修正後、上記の実エンジン再現試験が成功した。候補を全列挙しても、通信契約が壊れていれば合法な選択がすべて「違法」と分類される。このため、互換性不明の要求を探索完了として扱わない。

## 局所循環を除去できる条件

この監査で確認したのは、固定プリセットの標準`Link.AddProcedure`による一つの素材選択取引である。一般の盤面の同一視ではない。

適用する場合は、次の条件をすべて保持する。

1. 固定プリセットのLinkモンスターを、メインフェイズの明示的な特殊召喚候補から選んだ取引である。使用するカード・補助Luaスクリプトが監査対象と同じであることをハッシュで確認する。
2. 比較対象は同じ取引内の選択状態、またはその取引開始直前のメインフェイズ選択状態に限定する。他の経路や効果発動をまたいで比較しない。
3. 途中の生メッセージを`HINT`、`SELECT_UNSELECT_CARD`、取り消し後の`SELECT_IDLECMD`だけに限定する。チェーン、効果発動確認、別種の選択、移動、配置、カウンター、LP変化などがあれば除去しない。
4. pending要求全体、両者の全ゾーン、フィールドクエリ、LP、チェーン、ターン、フェイズ、状態が一致する。カード位置を対称だからという理由で統合しない。
5. 監査対象スクリプトの外へ出た場合は通常の深さ制限とfrontierに戻す。

実試験のゾーンは山札・手札・モンスター・魔法罠・墓地・除外・EX。クエリフラグは公開APIの全`OcgQueryFlags`をORしたもの。全クエリでもHOPTやLuaの内部状態を一般には取得できないため、この比較だけを根拠に適用範囲を広げない。

`proc_link.lua`では素材グループを選択中に追加・削除し、確定後のOperationで初めて素材を送る。コード・マジシャンの追加素材判定は一時フラグを持つが、取り消し時の追加素材グループ削除でそれを解除する。このケースは独立した実試験も通過した。

## v2探索器への追加監査

- コード・オブ・ソウルの効果を使った枝が、盤面が同じでも使用済みのまま独立したfrontierへ到達する。局所循環の除去例にその経路が入らない。
- 取り消しループを丸ごと含む固定rootPrefixから探索してもサブ木が空にならず、取り消しなしのrootPrefixから探索した最終盤面集合と一致する。除去対象の祖先深さは必ずrootPrefix以降にある。
- ウィザード1枚・固定順・先攻の条件は完走した。seed 123の直接実行では94ノード、31終端、frontier 0、取り消し循環10件。これは同条件の結果であり、実戦の残り4枚や別の初動の完了には転用しない。
- 循環除去なしで作った途中保存をv1形式として再開し、既存の終端・拒否記録を保持した。再開後の最終盤面集合は直接v2で完走したものと一致し、保存経路の実エンジン再生も成功した。
- 補助スクリプトの読み取り内容が変わると、探索開始時に循環除去が無効になる。共有Luaファイルを変更せず、監査プロセス内の読み取りだけを差し替えて検証した。
- 異なるdeckOrderを渡して同じ途中保存を再開しようとすると拒否される。
- コード・マジシャンを含む素材選択サブ木で、選択・解除循環だけが縮約される。固定rootPrefixより前のメインフェイズへの取り消しは出口として残り、召喚出口から続きを実行するとウィキッドが成立し、コード・マジシャンの墓地効果確認まで到達する。

v1再開試験は、現在と同じカードデータ・Lua・通信契約で作った生の応答履歴を対象とする。v2は通信契約の識別子を記録し、識別子が変わった保存結果の継続を拒否する。識別子を持たない旧結果では、過去のcoreRetryを再試行する。これは応答エンコードの不具合からの回復であり、古いparserが候補自体を読み落とした記録や別版のルールの正しさまで保証しない。その場合は元の初動から再検証する必要がある。

## ドロー継続の追加監査

`node --test --test-name-pattern='chance audit' tests/search-enumeration-audit.test.mjs` → 3件成功。

- 誘惑の名前別308ドロー結果から除外先を分けた353後続を、全件、元の手札1枚と保存deckOrderから再生した。効果解決後のpending・盤面・残デッキ順のハッシュが元データと一致した。闇属性がない組合せで墓地へ送られたドットスケーパーの誘発も、判断待ちとして残った。
- Cat／Binderの39境界、1053ドロー結果について、物理コピーの1枚選択・2枚組合せを別の方法で全列挙し、名前別重みと分母を照合した。各境界の合計確率は1であり、違う境界同士の重みは合算しない。
- 39境界から各1結果を抽出し、開始手札からドロー承諾まで全履歴を再生した。すべて開始手札は1枚のまま、物理コピー総数はプリセット40枚のまま、prefixは元の境界より承諾1入力分長くなった。再構築した結果をkernelへ渡すと、既存ドロー直後のrootへ到達し、未解決frontierとして保存できた。
- 継続要約の完了行には残りfrontierがなく、未初期化・未解決chanceがある要約は`complete:false`だった。
- `node scripts/search-optional-draw-continuations.mjs --self-test`も成功。1枚・2枚ドローのroot再生、4＋4ノード再開と8ノード連続実行の一致、公平な割当、既存ドロー後に引いた誘惑による次のドローが新しいchance frontierになることを確認した。

この条件では実戦初手の残り4枚を山札から取り除いていない。初手5枚の初動率・成功率には転用しない。元の正順データでは、誘惑308結果の物理重み合計は741だが、除外先を分けた353行の重みを合計すると852になる。同じドロー結果に対するプレイヤーの異なる選択を重複して並べているためであり、選択別の行を一つの確率分布として足してはいけない。

元の`verifyAllure`の逆順probeは、DARKがある場合はドロー後の手札と合法除外候補までの確認で止まっていた。この指摘後、担当が`--audit-reverse`を追加し、逆順345件について全除外先または手札墓地送りまで実エンジンで解決した。`runtime/search-draws/reverse-resolution-audit.json`の345件すべてに検証済み記録があり、元のAllureデータのハッシュが現在も一致することを読み戻した。状態ハッシュが正順と一致する240件、不一致の105件がある。監査側でも一致・不一致から各1件を独立再生し、保存ハッシュとの一致を確認した。

最新の継続要約は正順353件・逆順345件・同名コピー選択3件を独立した701後続として保持し、初動セット・エンドの2件を合わせて703jobとなっている。全701後続の初回処理済み記録と`complete:false`を読み戻した。状態ハッシュが同じという理由で合流していない。いずれも保存されたdeckOrderに条件付けられた結果であり、未知の山札全順列や全ドロー境界の後続探索完了を保証しない。

同名DARK2枚のCat×2、Rabbit×2、Backup×2で手札index 1を除外する3枝の欠落は解消済み。両indexの合法性を6回の実解決で確認した後、担当がindex 1を独立jobへ追加した。`runtime/search-allure/same-name-copy-audit.json`の3routeすべてを監査側でも独立再生し、選択前の要求・盤面ハッシュ、ラベル、最終盤面を照合した。保存jobの最後の入力はいずれも`selection:[1]`、元のAllureデータのハッシュは一致し、各jobに初回4ノードの処理記録がある。観測結果が同じでも入力履歴を合流していない。

## 網羅性の表示条件

- `SELECT_TRIBUTE`のminを必要カード枚数として扱わない。`SELECT_SUM`の値もカード枚数と同じではない。0枚から全候補枚数までの部分集合を候補とし、合法性を実エンジンで判定する。
- 組合せ選択と並べ替えを区別する。前者は選択集合、後者は全順列を列挙する。同名カードの添字を名前だけでまとめない。
- 検証エラーとエンジン例外を区別する。RETRYには入力経路を残し、未対応要求・読み取り不明・処理例外は未解決frontierに残す。
- ノード数、応答数、深さ、時間の制限で停止した部分には、未生成の候補位置を含む再開情報を残す。
- 固定した山札順の探索完了を、全ドロー結果の完了と表示しない。fixtureは`PSEUDO_SHUFFLE`を使うため、seedを変えるだけで全ドロー結果を生成したことにはならない。
- 先攻終了ボタンの入力時点で探索を切らない。エンドフェイズの処理と選択を解決し、次のターンに入った最初の要求で切る。記録される最終盤面には次ターン開始時のドローが含まれ得る。

以上は探索器の正しさに関する検証であり、通常M∀LICEの全展開を探索し終えたという結果ではない。実際の完了判定には、対象初動ごとのfrontier・失敗・ドロー条件を別途確認する。
