# 2枚初動探索の配置対称性調査

通常の魔法・罠ゾーン0〜4の配置をまとめる候補はある。ただし、**通常SZoneだけを並べ替えて盤面を同一視する実装には、現時点で安全性の証明が足りない**。同じチェーンで使ったMTPとTBが墓地へ移る際、元の配置によって墓地配列の順番が変わることを実coreで確認した。伏せる行動を他の行動より先に移す方法には、固定カード内でも発動可能な効果を失う反例がある。

この文書は採用判断用の調査結果である。runner、kernel、カードデータ、Lua、WASMは変更していない。既存の配置枝・未探索frontierは削除していない。

## 対象と再現

- 固定プリセット：メイン40枚・EX15枚、カード名41種類。プリセットhashは `8d4d40bc085644f9150344c6237b4239a07ef69f1cc21631832b4b695b641095`。
- 先攻1ターン、相手の初手なし、未確定ドロー後は応答しない。実験で別の条件を使った箇所は以下に明記する。
- 追跡しない再実行用probe：`runtime/multi-search-symmetry/probe.mjs`。結果は同ディレクトリの `evidence.json`、参照位置の走査結果は `dependency-scan.json`。
- 実行：`node runtime/multi-search-symmetry/probe.mjs` → **成功**。配置100試行と反例3種を確認。`node --check runtime/multi-search-symmetry/probe.mjs` → **成功**。

probeは実coreのpending、両者の全7ゾーンを全公開queryフラグで照会した結果、field query、LP、phase、chain、logを比較する。通常SZoneの位置記述とその配列だけを置換し、位置によって順番が変わる合法選択肢は内容で整列して比較する。同名カードの個体、墓地順序、使用済み効果、異なる行動履歴の同値をこの比較から推定しない。

最後のケースは固定カードだけを使った人工的な途中盤面（RabbitとCatが場、MTPとTBが手札）からの試験であり、その盤面に到達する2枚初動ルートの証明ではない。実際のカード効果と同ターンセット条件で処理した。これは「SZoneだけを並べ替えれば全queryが一致する」という一般化への反例であり、墓地順によって最良展開が変わったという結果ではない。

同時に送られた2枚の墓地順をまとめる場合、後続の`SELECT_CARD`等で同じ個体を選ぶ添字対応まで必要になる。カード名で墓地をソートするだけでは、同名個体の来歴・対象関係・使用済み効果を保存したことにならない。

## 削減を拡張した場合の失敗反例

1. **全伏せを先に済ませる：固定2枚組で失敗。** プルリア＋霊王で、Main1のプルリア発動候補は霊王を伏せる前には存在し、伏せた後には消える。`c84192580.lua:14`の自分フィールド0枚条件による。セット位置の選び方と行動順の入れ替えは別である。
2. **手札の通常魔法を先に伏せる：固定カードの途中盤面で失敗。** Backup/Wizardを素材にContractをリンク召喚する直前、手札のテラ・フォーミングを残すとサーチ効果を発動できるが、伏せると発動確認が消える。`c37458564.lua:42`のコストは手札または表側フィールドの魔法であり、伏せ魔法は使えない。この試験も人工的な途中盤面を使う。
3. **固定外のカードや既存の列効果まで許す：実効果の成否が変わる。** 無限泡影を伏せ枠0から使った後、テラを枠0で発動するとサーチできず、枠1ならUNDERGROUNDをサーチできる。`c10045474.lua:58`、`:90`以降が、墓地へ移った後も列情報を保存して使う。場に無限泡影が残っていないことは安全判定にならない。無限泡影と相手モンスターを追加したこの反例は、固定プリセットの探索結果ではない。

## 提案する厳密な適用条件

実装候補は、**同じ完全入力prefixから出る一つの`SELECT_PLACE`で、同じカードを通常SZoneの空き枠へ置く選択肢の対称性**に限定する。以下は採用前に満たすべき条件であり、全部を検証済みという意味ではない。

1. プリセット、全Lua依存、カードDB、WASM、応答変換、モードを固定し、そのデュエルに追加された外部カード・効果がない。未知ドロー・相手干渉の境界を越えない。実行中の資産差し替えも受け入れない。
2. 選択は枚数1、同じプレイヤー、`location=8`、`sequence=0..4`のみ。Field/Pendulum/Monster/Extra Monster Zone、使用禁止枠、予約された枠、列や履歴位置を使う効果がある場合は適用しない。現在空いていることだけで無限泡影等の残留効果を否定しない。
3. **変えるのは配置だけ。** 通常召喚、特殊召喚、効果、手札コスト、罠のセット時期、チェーン順、任意発動、エンド移行を移動・削除しない。単なる終点盤面hashによる異なる履歴の合流もしない。
4. 元の配置枝と代表枝の間で、カード個体と全ての後続の合法応答に対応を持たせる。現在/以前のSZone位置に加え、実験で差が出た墓地順、そのほかの移動先配列の添字も対応対象とする。効果使用回数、コスト、カードの対象関係、各種フラグ、LP、乱数を含む後続処理を保持する必要がある。
5. 保存する証拠は同じprefixからの局所的な対応関係とする。代表枝に対応する後続が本当に検索対象に残ることを確認し、固定rootより前の祖先や別shardに存在するはずの経路を根拠に枝を消さない。
6. 対応を定義していないprompt/message、複数カード移動、異なる合法候補、未知の依存に遭遇した場合は、元の配置prefixを復元して通常探索へ戻す。**未証明の省略枝を未探索として保存したまま、代表枝だけの完了を全体完了にしない。**
7. 対称性の方針と証明範囲に版を付け、checkpointに省略した配置・対応・件数を残す。完了表示は「この対称性で同じと証明したパターンを代表させた、無ドロー範囲の完了」とする。nativeに渡す代表ルートは従来どおり元手札から実coreで再生して確認する。

特に条件4は未完了である。80試行の一致だけを根拠にスキップしてはいけない。墓地順の反例を回帰試験にし、対応する各個体の後続選択を独立に解決する試験と、固定効果の参照条件の検証が必要になる。

隣接する2回の手札SSetを入れ替える候補は別の規則として扱う。両方の順序が元のprefixで合法、途中の全選択・イベント・コストを調査済み、最後に同じ個体状態へ到達し、途中で終了する枝と他の行動を挟む枝が残ることが必要になる。霊王＋密告の40試行が一致したことは、この限定例の証拠であり、任意のセット順をソートする根拠にはならない。

## 採用判断に残るもの

通常SZone位置の代表化には削減余地がある。しかし現在の観測状態・生入力添字の契約では、SZoneの置換だけで後続をそのまま共有できない場合がある。まず上記の個体・添字対応を定義し、失敗時に元の枝を取り戻す範囲で検証するのが提案である。採用はrootが判断する。

同梱`runtime/MDPro3/Tools/YGO Classes/ocgcore/operations.cpp:2417`には、SSetがゾーン選択・セット状態・イベント処理を行う実装があり、`card.cpp:1254`にはMZoneのリンク判定がある。ただし同梱C++と実行中WASMのビルド同一性は確認していないため、参考資料としてのみ用いた。実際の成否は上記WASM実行で確認した。

この調査は全木の有限性を証明していない。時間・訪問数・深さの上限で終わったfrontierや、対称性が未証明の配置枝は、引き続き未探索である。

## 追加調査：応答の別名と未使用の同名カード

`SELECT_PLACE`の候補は、通常SZoneの5枠、MZoneの5枠とも、それぞれ異なる`{player,location,sequence}`へ符号化される。後述の4試験で観測した配置prompt計75個でも、候補数と異なるwire応答数がすべて一致した。**同じ応答を別の入力名で表しているために無条件で消せる配置枝は、この範囲にはなかった。** リンク関係が変わらない通常SZoneの選択でも、前述した墓地順序の差は残る。

`node runtime/multi-search-symmetry/copy-alias-proof.mjs` → **成功**。`copy-alias-evidence.json`へ保存した。最初のデッキ選択だけを対象に、黄金櫃＋霊王では38個体・25カード名、UNDERGROUND＋霊王では13個体・8カード名を確認した。重複する10グループ・計28個体の選択では、同名グループ内の選択前queryと選択直後の全query/pending/logがそれぞれ一致した。対象はデッキに最初から連続して置かれ、そこから一度も移動していないコピーである。

この一致だけで一般の同名カードをまとめていない。queryで見えない効果の個体参照、付与効果、使用履歴、戻されたカード、別のデッキ順、後続の同名個体選択まで保存する証明が必要になる。手札・場・墓地の同名カードや、同名だからという条件だけの処理には適用できない。

小さい閉じた例は追加で全探索した。**黄金櫃＋霊王、最初の黄金櫃を枠0で発動し、デッキのUNDERGROUND3コピーのいずれかを除外する3prefix**について、各13ノード・6終端・frontier 0で完走した。除外選択以降の全入力suffix、最終盤面hash、logの集合が3者で一致した。集合hashは `1f35d6352939e4b17f1286130b21d00d154baa402c92c4e3113e1803cc8212d9`。

これはその3つの完全指定prefixと先攻1ターンの証明である。証明を作る際には3本とも探索しているため、初回探索の実行量は削減していない。将来の再利用は保存した完全prefix・手札・seed・ルール資産と一致する場合に限られ、別の初動や途中状態へ一般化しない。3コピーをまとめれば残り全ペアを処理できる、という結果ではない。

## 追加提案：1候補の連続処理で再生回数を減らす

**カード状態を同一視せずに適用できる改善は、選択肢が厳密に1個だけのpromptを同じDuel内で続けて処理する方法である。** 現在のkernelは子prefixごとに新しいDuelを作って先頭から再生する。分岐がない区間だけその作り直しを省けば、隠れた使用済み効果やLua状態は元の実Duelでそのまま維持される。唯一の候補も実coreの受理を確認し、RETRYや例外を合法と推定しない。

研究用APIは `runtime/multi-search-symmetry/unary-proof.mjs` の `unarySearch({hand,prefix,maxDepth,maxNodes,maxGenerated,maxMs})`。**既存kernelの置換、checkpoint移行、自動入力への接続は行っていない。** 再現コマンド `node runtime/multi-search-symmetry/unary-proof.mjs --run` は成功し、結果は `unary-evidence.json` に保存した。

各試験で既存kernelを比較対象とし、全終端の入力prefix・最終hash・log、全未探索/ドロー境界prefix、拒否prefix、論理訪問数が一致することを検査した。比較の途中で時間・訪問数・生成数の上限に達した場合は同値判定を受理しない。深さ6・4の試験は、その深さまでの木と残したfrontierの一致であり、全ターン完了の証明ではない。比較時には両側とも既存Link UI循環縮約を無効にした。

| --- | ---: | ---: | ---: | --- | --- |
| 霊王＋密告、完了木 | 114 | 114→74 | 443→243 | 51 / 0 / 0 | 1.844→1.210秒 |
| 誘惑＋Code Magician、無ドロー範囲完了 | 24 | 24→24 | 53→53 | 6 / 0 / 10 | 0.381→0.376秒 |
| Rabbit＋TB、深さ6まで | 715 | 715→665 | 3694→3444 | 101 / 325 / 0 | 11.076→10.682秒 |
| 黄金櫃＋霊王、深さ4まで | 870 | 870→870 | 3214→3214 | 156 / 485 / 0 | 13.500→13.736秒 |

Duel生成の削減は、この4例合計で1723→1633回、約5.2%。罠だけの木で約35%、Rabbitの浅い木で約7%、他2例では0%だった。時間は単発計測で、同時実行負荷やGCに左右される。生成数が同じ黄金櫃の例は速くなっていない。したがって、全333組の探索量が桁違いに減るとは評価しない。

本実装へ取り込む場合に維持する条件は次のとおり。

1. 既存のプロトコル検証と候補列挙を通った**候補数1**の区間だけを連続処理する。「強い候補が1個」「他の候補はおそらく違法」は対象にしない。
2. 各promptでドロー・相手判断・ターン終了・エラー・予算を検査する。未知ドロー後は一切応答しない。各中間ノードのMain1評価とobserverを省略しない。
3. 全入力を通常のroute.stepsへ記録する。論理訪問数、生成したprefix、端点を維持し、Duel生成回数・再生入力数だけを別の性能指標として数える。
4. 途中で止まった場合は、その時点の完全prefixを再開可能なfrontierに残す。唯一候補が続く循環を完了と呼ばない。
5. 既存の局所Link UI循環検出と組み合わせる際は、その取引状態を引き継ぐか、対象取引中はこの連続処理を使わない。今回の比較は既存UI縮約との併用を検証していない。
6. 研究版はproduction用のresume/世代管理を実装していない。採用時はcheckpoint方針の変更として扱い、旧frontierを消さず、既存版と一致する回帰試験を行う。

この方法は選択枝の数を減らす規則ではなく、同じ木を実行するための再生コストを抑える規則である。公開queryに現れない状態を理由にした不確かな合流が要らない点が利点だが、現時点で残りの未完了ペアを完走できる保証はない。

実行済みprobeとJSONのSHA-256、固定された探索ソース・ルール資産の識別情報は `runtime/multi-search-symmetry/provenance.json` に保存した。今回の追加調査でもrunner/kernel/資産、既存frontier、native自動入力の挙動は変更していない。
