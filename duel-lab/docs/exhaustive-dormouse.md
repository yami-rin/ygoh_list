# Dormouse単独の分岐探索

固定40＋15枚、先攻の自分メインフェイズ1、手札はDormouse1枚のみ、相手盤面と初手は空、相手の妨害なし。初手カードは固定デッキから抜き取るため、デッキ内のDormouseは0枚です。実際のルールエンジンを使い、元の手札から全入力履歴を再生して検証します。

**全展開木の探索完了ではありません。** 最初の除外効果の処理だけを明確に区切って網羅し、以後の未探索枝を保存しています。同じカード名・見えている盤面・左右対称の配置を理由に状態を統合していません。名称ターン1、デュエル中1度、特殊召喚制約を含め、履歴を再生したエンジンの判定を使います。

## 初回効果の限定全探索

通常召喚位置5か所からDormouseの効果を使うと、除外候補はRabbit3個体・Cat3個体・Hare1個体の合計7個体です。種類が同じでも山札内の個体と選択indexを保持し、**35本の除外prefix**から探索しました。

帰還・回収の任意発動、帰還位置、攻撃／守備表示、Rabbitの任意セット、罠3種類と伏せ位置まで展開すると、**2,870ノード、2,080本の葉**になりました。葉では次のメイン行動、または最初の罠を使えるチェーン応答窓で止めています。

| 最初の除外先 | 葉の数 | 数え方 |
| --- | ---: | --- |
| White Rabbit | 1,935 | 通常召喚位置5 × 個体3 ×［帰還しない1 ＋ 帰還位置4 × 表示形式2 ×（セットしない1 ＋ 罠3 × 伏せ位置5）］ |
| Cheshire Cat | 135 | 通常召喚位置5 × 個体3 ×［帰還しない1 ＋ 帰還位置4 × 表示形式2］ |
| March Hare | 10 | 通常召喚位置5 ×［回収しない1 ＋ 自身を回収1］ |

全2,080葉の入力列・履歴hash・位置・対象個体・盤面hash・未決prompt hashを `routes/exhaustive-dormouse.json` に保存しています。詳しい盤面とpendingを含む再開用資料は `runtime/search-dormouse/first-stage-frontier.jsonl` です。

開始直後の「ターン終了」「モンスターセット」や、除外効果より先にL1を出す枝は、この初回効果の網羅範囲に含めていません。別の `rootAlternatives` に26本の実再生済みprefixとして保存しました。内訳は初手終了1、セット位置5、通常召喚位置5×［L1の3種＋終了］です。このうち先攻1ターンが終わる6本は終端、残り20本は未探索frontierです。

## 後半EXの不足監査

既存のDormouse6ルートを独立再生し、完全履歴216ノードを監査しました。既存ルート中に召喚選択肢へ現れていても、一度も選んでいないEXは次の5種でした。

- リングリボー
- 転生炎獣アルミラージ
- サイバース・コントラクト・ウィッチ
- W：Pファンシーボール
- パーフェクトロン・ハイドライブ・ドラゴン

カードコードは順に24842059、60303245、37458564、4993187、13203964です。各EXが提示された全64局面を独立seedとして、素材・配置の候補を実coreで探索し、**6,321ノード、対象EX召喚までの1,189履歴**を確認しました。5種類すべての代表ルートを独立再生済みです。未探索frontierは5,139本です。対象EXが場へ出た時点も「到達確認した未探索frontier」であり、その召喚時効果や後続が全て終わった盤面とは扱いません。

既存ルートが実召喚した10種と合わせると、**固定EXの15種類すべてをDormouse1枚・追加ドローなしでそれぞれ召喚できる**ことが確認できました。これは15体の同時展開、最善性、すべての素材・配置の網羅を意味しません。`--verify` は15種の集合が固定EX全体に一致することも検査します。

## 初期の均等探索の記録

`--frontier` は初段の全2,080葉へ予算を均等配分します。10,000ノードなら各葉4または5ノードです。各呼出しは最大30秒、絶対入力深度180、ドローが発生した枝は別途引き継いで停止します。kernel v2以降は、固定script・同一の標準Link取引・盤面とpending等の完全復元を確認した無作用UI往復だけを縮約します。ゲーム中の状態や使用済み効果を同一視する処理ではありません。それ以外の未探索枝はfrontierへ残し、版・policy・縮約数をcheckpointに記録します。

枝別checkpointは `runtime/search-dormouse/continuation-<historyHash>.json`、集計は `continuation-summary.json` です。再度実行すると既存checkpointから各枝を追加探索します。`routes/exhaustive-dormouse.json` の `complete:false` は全展開の未完了を意味します。

初回の公平な配分は全2,080葉に計10,000ノード、179.25秒（約55.8ノード/秒）で完了しました。未着手の葉は0、残るfrontierは23,000、ドロー境界は0でした。この探索量ではまだドローに至る深さへ到達したとはいえません。最新の累積値は成果物の `continuationSearch` が正本です。

v2でさらに10,000ノードを208.08秒で再開し、**継続探索は累計20,000ノード、先攻1ターンの終端70本、frontier44,073本**になりました。検証済みのLink召喚取消35往復だけを除去し、ドロー境界は引き続き0です。初段と不足EX探索を合わせた訪問回数は29,191です。これは祖先の再生重複を含み、独立した盤面数ではありません。

上記は分割方式へ移行する前の測定記録です。現在の保存結果を再開するときは、次節の `--partition --no-publish` と `--aggregate` を使用します。引数なしの初段再生成で既存集計を上書きしないでください。

`--deep` の1 seed当たりノード数は `DORM_SEARCH_NODES`（既定100）、追加入力深度は `DORM_SEARCH_DEPTH`（既定12）で指定できます。探索数は検証した履歴ノードの訪問回数であり、重複を除いた盤面数や勝率ではありません。

## 重複しない並列深掘り

分割対象は初段2,080葉と未解決の開始直後20枝の**計2,100**です。成果物内の安定した順番をglobalIndexとし、`globalIndex % DORM_PARTITION_COUNT` で割り当てます。4分割なら各525枝で、重複・欠落はありません。既存の先攻1ターン終端6本は別枠で保持します。

各担当は区画indexだけを変えて、次を実行します。全担当のCOUNTを4へ統一してください。

```powershell
$env:DORM_PARTITION_COUNT='4'
$env:DORM_PARTITION_INDEX='0' # 他の担当は1、2、3
$env:DORM_LEAF_NODES='16'
$env:DORM_LEAF_MAX_MS='30000'
$env:DORM_MAX_DEPTH='180'
Remove-Item Env:DORM_PARTITION_OFFSET,Env:DORM_PARTITION_LIMIT -ErrorAction SilentlyContinue
node scripts/exhaustive-dormouse.mjs --partition --no-publish
```

各呼出しで、担当する各葉に最大16ノードを追加します。1葉の処理時間は30秒以下です。`DORM_PARTITION_OFFSET` と `DORM_PARTITION_LIMIT` はその区画内の処理範囲を絞るための値で、通常は指定しません。`--dry-run` を加えると対象一覧だけを表示します。

workerは各葉のcheckpointと `runtime/search-dormouse/partitions/p4-0.json` 等の区画専用進捗だけを書きます。`--partition` は常に共有publicationなしで、`--no-publish` はその動作を明示する指定です。同一区画・同一checkpointにはプロセスlockを設けています。異なる区画のworkerが共有の集計JSONを書き合うことはありません。

ドロー、相手の選択、同じ深度上限で止まった枝だけが残る葉は再処理せず、境界を保持します。未探索枝も混在する場合はその枝を先に処理します。scriptやprotocolの更新で再検証すべき候補はそのままkernelに渡します。

全workerの終了後、集約担当だけが次を実行します。

```powershell
node scripts/exhaustive-dormouse.mjs --aggregate
node scripts/exhaustive-dormouse.mjs --verify
```

集計は固定2,100件のcheckpointを直接読み、未着手もfrontier1本として数えます。版2の集計へ移行後は旧 `--frontier` が集計を上書きしないよう拒否し、再開には `--partition` を使います。集約は稼働中にも読み取れますが、その場合は各checkpointを読んだ時点のsnapshotであり、全体が同時刻に停止した結果ではありません。

4個の実core workerを1ノードずつ同時実行し、4区画×525件＝2,100件の一意な割当、共有routes/summaryのSHA不変、開始直後の別ルートの処理、単独集約、実再生検証が成功しました。検証スクリプトは `runtime/search-dormouse/partition-smoke.mjs` にあります。

本実行の4区画は全2,100件を処理し、それぞれ8,232／8,304／8,352／8,304ノードを追加しました。区画ごとの実行時間は約257〜268秒です。同一区画の二重起動拒否と、`--aggregate --no-publish` の誤併用時に共有JSONを変更しないガードも確認しました。

全worker終了後の集約・検証はPASS。継続探索は累計53,198訪問、終端5,664本、未探索frontier82,994本、未着手0、失敗0です。初手終了・セットの6終端は別枠です。全2,100 checkpointの照合、35本の初段根と代表8ルートの独立再生、EX15種類への個別到達集合一致を確認しました。全展開の完了を意味する値ではありません。
