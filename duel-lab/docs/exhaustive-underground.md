# UNDERGROUND / テラ・フォーミングの後続探索

この成果物は、実際のルールエンジンで入力履歴を列挙する**再開可能な探索**である。全展開の列挙完了や最強盤面の証明ではない。最新の計数は [exhaustive-underground.json](../routes/exhaustive-underground.json) の `search` を参照する。

## v2での追加探索

未着手だった25入口を先に処理し、その後に既存入口の深い継続を実行した。新しいNodeプロセスでprotocol識別子とハッシュを取得し、全412checkpointをv2へ移行した。

| 項目 | 結果 |
| --- | --- |
| 元未着手25入口の追加訪問 | 1,000 |
| 既存入口の深い継続の追加訪問 | 14,429 |
| 今回の追加訪問合計 | 15,429 |
| 以前からの累積prefix訪問回数 | 27,494 |
| checkpointを作成・更新した入口 | 412/412 |
| 個別探索完了／未着手 | 27／0 |
| 保存frontier | 28,653 |
| 未完了として保持したドロー境界entry | 106 |
| ドロー直前の異なるprefix | 38 |
| 検証済みLink UI往復の縮約回数 | 3,060 |
| protocol検証済みcheckpoint | 412/412、ハッシュは全件一致 |
| engine/tool失敗・core拒否 | 0・0 |
| 最後に独立replayした代表ルート | 240 |

探索・最終再検証・保存は約712秒。`runtime/search-underground/v2-verification.json` に、旧25入口が先に並んだこと、追加深掘りが1万node以上であること、全protocol一致、ドロー境界を完了扱いしていないことのassert結果を保存した。異なるジョブの入力履歴は重なるため、訪問数を異なるコンボ数として扱わない。

全入口に着手したことと、全入口の探索が完了したことは異なる。全体は引き続き `complete: false` であり、残ったfrontierから再開できる。

## 条件

- 固定のメイン40枚・EX15枚から、初期手札に置く1枚を正確に差し引く。
- 先攻1ターン目。相手の初期手札と盤面は空で、相手の妨害は加えない。
- 対象は `M∀LICE IN UNDERGROUND` と `テラ・フォーミング`。追加の初期手札や手札コストを補充しない。
- 任意ドローを選ばない側も探索する。ドローを選んだ側は、最初のドロー解決時点で止めて別のドロー組合せ探索へ渡す。
- 素材・対象・配置・表示形式・効果発動の可否を、共通kernelが実coreの候補から列挙する。同名の別コピーも別indexとして保持する。

## 黄金櫃と分ける理由

UNDERGROUNDは発動解決後もフィールドに残る。コントラクト・ウィッチの儀式モンスターサーチで、表側のUNDERGROUNDを墓地へ送るコストにできる。一方、黄金櫃は発動後に墓地へ行くため、この時点のコストを同じ条件では供給しない。

テラ・フォーミングはUNDERGROUNDをデッキから1枚減らし、テラ・フォーミング自身を墓地へ置く。後の墓地対象、山札の残数、ドロー候補に差が出るため、UNDERGROUNDと同じ開始状態にまとめていない。

## 初回除外と深い分岐への入口

両初動で実coreが提示した初回除外の13 indexを、一つずつ選択して解決まで進むことを検証した。カード名としては下級4種類・罠3種類・UNDERGROUNDの8種類である。結果と次のpromptをJSONの `initialBanishCoverage` に保存する。

テラ・フォーミングでサーチする同名UNDERGROUNDの3コピーのうち、個別probeは既存ルートと同じ1コピーから行う。他のサーチindexは `whole-opening` の未展開frontierに残る。これらのドロー順序まで同じであるとは仮定していない。

初動の先頭だけを深く掘る偏りを抑えるため、検証済みルートの途中を探索の入口にもする。

- Rabbit先除外／Dormouse先除外からのS:P・WHITE BINDER到達線。
- コントラクト→コード・マジシャン→ウィキッドの素材・魔法コスト・墓地送り・墓地除外対象。
- バックアップのサーチと捨てるカード、WHITE BINDERの墓地除外と罠セット。
- Hare自己回収からWHITE BINDER・TBを経由する代替線。
- 各線のリンク素材選択、配置、表示形式、任意効果の選択。

既存線の最終盤面だけでなく、その途中でcoreが複数候補を提示した箇所を入口にする。各入口は同じ上限で探索し、候補の残りを保存する。入口同士の木は重なり得るため、訪問数は「重複を除いたゲーム状態数」や「異なるコンボ数」ではない。

## 状態の取り扱い

見た目が同じ盤面でも、名称ターン1の使用履歴、召喚制限、処理途中の選択状態が異なる可能性がある。このため盤面ハッシュによる探索の枝刈りはしていない。盤面の重複をまとめるのは、出力する代表ルートだけである。

代表ルート数には保存上限があるが、これを探索の枝刈りには使わない。全terminal route、拒否された応答、エラー、未展開履歴は各checkpointに残す。

v2では共通kernelの検証済み規則を使い、同じ標準リンク召喚の素材選択中に起きた、状態を変えない選択→解除や召喚キャンセルの往復だけを縮約する。対象scriptのハッシュ、同一取引、core全query・LP・フェイズ・チェーン・ログ・pending不変をkernelが確認する。それ以外の反復は深さ上限で止めてfrontierに残す。縮約規則と回数、protocol識別子・ハッシュ、旧checkpointの移行情報は各checkpointと要約に保存する。

`complete: false` は、残った上限や対象外の枝が存在することを明示する。個別の何もしない除外枝が先攻終了まで解決していても、全体の完了とは扱わない。

## ドロー担当への引き渡し

`runtime/search-underground/draw-frontier.json` の各項目に以下を保存する。

- `hand` と、ドローを解決する応答の**直前**までの `prefix`。
- ドロー解決を引き起こした `drawResponse`。
- その直前の実coreから取得した `remainingDeckCodes`。
- 固定fixtureでドローした後の参考盤面。そこからの追加展開は探索しない。

ドロー前の山札をprefixから再現して読むため、展開中のサーチ・墓地送り・除外による残数の変化を含む。固定fixtureの1通りの結果を、全ドロー結果や確定初動として採用しない。

## 実行と再開

リポジトリの `duel-lab` で実行する。

```powershell
node scripts/exhaustive-underground.mjs --prepare-only
node scripts/exhaustive-underground.mjs --nodes=500 --per-job=4 --ms=120000
node scripts/exhaustive-underground.mjs --resume --nodes=18000 --per-job=40 --depth=128 --ms=900000 --representatives=240
```

`--nodes` と `--ms` は今回の探索ループ全体の上限、`--per-job` は各入口の訪問上限、`--depth` は初期手札から数えた応答数の上限である。入口の準備と最後の代表ルート再検証は時間上限に含めない。上限を広げて `--resume` すれば保存した未展開履歴から進む。再開時はcheckpointのない未着手の入口を先に回し、時間上限のため毎回同じ入口だけを深く掘ることを避ける。

主な保存先は以下のとおり。

| 保存先 | 内容 |
| --- | --- |
| `routes/exhaustive-underground.json` | 条件、上限、集計、初回除外の検査、独立replay済み代表ルート、未着手ジョブ |
| `runtime/search-underground/manifest.json` | 全入口のprefixと出所、元データのハッシュ |
| `runtime/search-underground/<id>.json` | kernelのvisited・frontier・bounds・terminal・拒否応答・失敗 |
| `runtime/search-underground/draw-frontier.json` | ドロー結果の全組合せを別途調べるための前状態 |

runtimeはGit対象外なので、別PCではコマンドから生成する。ソースルートと保存する代表ルートは、毎回、独立した実coreで入力列をreplayして最終盤面ハッシュまで検証する。Astra CLIや対戦プロセスはこのスクリプトから起動しない。
